# 知枢（DocuMind）本地知识库智能问答 Agent —— 技术设计文档

> 面向简历 / GitHub 展示的项目技术梳理，可作为面试讲解提纲。

## 一、项目概述

### 1.1 背景

大语言模型（LLM）虽具备强大的自然语言理解与生成能力，但存在两个明显短板：一是**知识时效性与私有性**——模型无法直接回答企业内部文档、公司制度等私有数据；二是**无法执行动作**——模型不能自己查数据库、做精确计算。业界主流方案是结合检索增强生成（RAG）与函数调用（Function Calling）来补齐这两块能力。

当前开发者往往直接套用 LangChain、LlamaIndex、Dify 等框架快速搭建，但框架屏蔽了大量底层细节，导致「会用」与「会做」之间存在鸿沟。

### 1.2 目标

本项目**从零手写**一个本地知识库智能问答 Agent「知枢（DocuMind）」，不依赖任何 Agent/RAG 框架，目标是：

1. 实现**多工具自动路由**：模型根据问题自动判断该「算数 / 查数据库 / 查文档」。
2. 实现**手写 RAG**：本地文档向量化入库，检索后带引用回答。
3. 实现**多轮会话持久化**：对话历史存 MySQL，刷新 / 重启不丢失。
4. 提供**可视化界面**（Gradio）与 **REST 接口**（FastAPI）两种入口。

## 二、需求分析

| 编号 | 功能需求 | 说明 |
| --- | --- | --- |
| F1 | 数学计算 | 用户提问算术表达式时，安全计算并返回结果 |
| F2 | 结构化数据查询 | 用户问商品/库存等问题时，模型自动生成只读 SQL 查询 MySQL |
| F3 | 文档知识问答 | 用户问制度/政策等内容时，检索本地知识库并带引用回答 |
| F4 | 多轮上下文 | 指代消解（如「那再加 5 呢」）依赖历史对话 |
| F5 | 会话管理 | 新建 / 切换 / 删除会话，历史持久化 |
| F6 | 流式输出 | 逐 token 输出，提升体验 |
| F7 | 多格式入库 | 支持 .md / .txt / .docx / .pdf 文档入库 |

**非功能需求**：核心逻辑自研（不用框架）；安全性（防 SQL 注入、防代码执行）；本地可运行、低成本。

## 三、技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 大模型 | DeepSeek `deepseek-chat` | 中文能力强、价格低，提供 OpenAI 兼容接口 |
| LLM SDK | `openai` | 一套 SDK 兼容多家，只改 base_url 即可切换 |
| 后端 | FastAPI | 原生支持 SSE 流式，自动生成接口文档 |
| 前端 | Gradio | 极少量代码即可做出可视化界面 |
| 向量库 | Qdrant（本地嵌入模式） | 文件级存储免 Docker，切服务器模式只需改配置 |
| 向量模型 | `bge-small-zh-v1.5` | 中文检索专用，本地离线、免费 |
| 会话存储 | MySQL | 与 `query_db` 工具共用一个库，减少依赖 |
| 文档解析 | python-docx / pdfplumber | 覆盖常见办公文档格式 |

## 四、系统架构

```
            ┌─────────────────────────────────────┐
            │        接入层（两个入口）               │
            │  Gradio 界面    /    FastAPI REST    │
            └───────────────┬─────────────────────┘
                            │ run_agent / run_agent_stream
            ┌───────────────▼─────────────────────┐
            │      Agent 核心（手写 ReAct 循环）      │
            │   模型判断：直接回答 or 调用工具？        │
            └───┬──────────┬───────────┬──────────┘
                │          │           │
         ┌──────▼──┐ ┌────▼─────┐ ┌───▼────────────┐
         │calculate│ │ query_db │ │search_knowledge_base
         │AST白名单 │ │SELECT只读│ │   └─ RAG 流水线
         └─────────┘ └────┬─────┘ └───┬────────────┘
                          │           │
                   ┌──────▼───┐  ┌────▼──────────┐
                   │  MySQL    │  │ Qdrant + bge  │
                   │ products  │  └───────────────┘
                   │ sessions  │
                   │ messages  │
                   └──────────┘
```

核心思想：**模型只负责「决策」与「表达」，执行权始终在应用侧**。模型通过 Function Calling 输出「要调用哪个工具 + 什么参数」，由代码真正执行并把结果以 `role="tool"` 喂回，循环往复直到模型给出最终答案——这就是 ReAct（推理 + 行动）范式。

## 五、核心模块详细设计

### 5.1 Agent 循环（`app/agent.py`）

```
用户提问 → [模型：要不要调工具？]
   ├─ 不调 → 直接返回答案
   └─ 调   → 执行工具 → 结果 role="tool" 喂回 → 再问模型 → …（上限 5 轮）
```

关键点：

- **多轮对讲**：每轮都带 `tools` 参数发给模型，模型自主决定「直接回答」还是「喊工具」。
- **tool_call_id 对齐**：工具结果必须带上模型给的 `tool_call_id`，否则 API 报错。
- **流式版缓冲**：流式场景下模型喊工具前会先吐一句「思考」，需先缓冲；若本轮有工具调用则丢弃该文本，避免泄露给用户。

### 5.2 工具集（`app/tools.py`）

三个工具 + 一张「电话簿」（工具描述 JSON，发给模型）：

| 工具 | 功能 | 安全设计 |
| --- | --- | --- |
| `calculate` | 四则运算 | `ast` 白名单节点 + 空 `__builtins__`，杜绝任意代码执行 |
| `query_db` | 只读查 MySQL | 仅允许 `SELECT`、拒绝分号多语句注入 |
| `search_knowledge_base` | 文档检索 | 懒导入，非文档场景不加载 embedding 模型 |

### 5.3 RAG 流水线（`app/rag.py` + `app/embedder.py`）

```
入库：文档 → 魔法字节嗅探类型 → 抽文本 → 标题切段 → 句边界切块(overlap) → bge 向量化 → Qdrant
检索：提问 → 向量化(带 query 前缀) → Qdrant top_k → 拼【资料】→ 模型带引用回答
```

关键点：

- **切块质量决定检索质量**：先按 Markdown 标题切段（章节自成一体），再段内按句边界切块并留 overlap，避免句子被拦腰截断。
- **query 前缀**：bge 官方推荐检索时给 query 加「为这个句子生成表示以用于检索相关文章：」前缀，文档侧不加。
- **多格式解析**：不只看扩展名，用「魔法字节」（`%PDF`、`PK`）嗅探真实类型，docx 额外抽取表格内容。

### 5.4 会话管理（`app/session_store.py` + `app/main.py`）

```
sessions (id, title, created_at, updated_at)
messages (id, session_id, role, content, created_at)  —— FK 级联删除
```

- 两张表，`messages.session_id` 外键 `ON DELETE CASCADE`，删会话自动删消息。
- `get_messages(session_id)` 返回 OpenAI 风格 `[{role, content}]`，可直接喂给 `run_agent(history=...)` 做多轮上下文。
- FastAPI 提供 `POST/GET/DELETE /sessions` 及 session-aware 的 `/chat`、`/chat/stream`。

## 六、关键难点与解决方案

| 难点 | 解决方案 |
| --- | --- |
| gradio 4.44.1 强制依赖 gradio_client 1.3.0，Python 3.9 升不了 gradio 5，存在 schema 解析 bug | 组件「同时作为事件输入+输出」时 `additionalProperties: true` 导致 `get_api_info()` 崩溃；monkey-patch 补布尔分支 |
| embedding 离线加载 | gradio import 时连带固化 `HF_ENDPOINT`，须在 `import gradio` 前设镜像 + 离线开关 |
| DeepSeek 流式 + 工具调用的「思考」泄露 | 缓冲本轮文本，有工具调用则丢弃 |
| Qdrant 本地模式单进程锁 | 测试时先停掉正在跑的进程，避免「已锁」报错 |
| 模型生成 SQL 的注入风险 | 只读白名单 + 拒分号（生产级还应加只读账号 + 连接池） |

## 八、总结与展望

### 总结

本项目完整走通了「LLM + Function Calling + RAG + 会话管理」这一 Agent 应用的核心链路，且全部核心逻辑手写实现。相比直接套框架，深刻理解了：

1. ReAct 循环的本质——模型负责决策，应用负责执行；
2. RAG 中「切块质量决定检索质量」的工程经验；
3. 流式、持久化、多格式解析等真实工程细节。

### 展望

- 混合检索（关键词 + 向量）与重排序，进一步提升检索精度；
- 多用户鉴权与生产化部署（Qdrant 服务器模式、uvicorn 生产配置）；
- 数据库 schema 自动生成工具描述，摆脱硬编码表结构；
- 接入更多数据源（网页、音视频转写等）。
